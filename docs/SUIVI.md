# Suivi du projet — KOTI

Document de pilotage. À mettre à jour à chaque livraison (sections 2, 3, 4 et 6).
Dernière mise à jour : 08/11/2026.

Liens : [PRD](PRD.md) · [Architecture et décisions](ARCHITECTURE.md) · [README](../README.md)

## 1. Où en est-on ?

**Phase 1 — Frontend sur données simulées : livrée.** Toute l'application est utilisable de bout en bout
(création → invitation → adhésion → cotisation → déclaration → validation → tour de main → historique)
avec des règles métier et des permissions réelles, appliquées côté serveur.

**Phase 2 — Backend réel (PostgreSQL, Drizzle, Better Auth) : en cours.** PostgreSQL et Drizzle sont en service (08/11) ; Better Auth, les e-mails et les notifications push sont en service ; il reste les SMS et la mise en ligne. Démarrée après retour des premiers
utilisateurs sur l'interface et arbitrage des questions ouvertes (section 4).

| 09/11/2026 | **Erreurs non gérées : message générique pour l'utilisateur, détail complet dans les journaux.** Utilisateur : jamais de texte technique, seulement « Une erreur inattendue est survenue… » avec un **code de référence** (`E-7K2P9Q` pour une action, le `digest` Next.js pour une page) à communiquer à l'équipe ; les erreurs métier voulues (règles de gestion) gardent leur message. Administrateur : journal technique (`src/server/log.ts`) — une ligne **JSON** par événement en production (terminal lisible en développement) avec le code de référence, l'erreur et **toute sa chaîne de causes**, les détails PostgreSQL (contrainte, table, code), la pile d'appels, la requête concernée (méthode, route, agent) et l'utilisateur. Toute erreur de page, d'action ou de route d'API est captée par `onRequestError` (`instrumentation.ts`), les arrêts brutaux du processus aussi. **Confidentialité des journaux** : valeurs des requêtes SQL coupées, mot de passe des adresses de connexion et secrets écrits en clair masqués, clés sensibles (mot de passe, jeton, cookie…) jamais journalisées. Les messages bruts du navigateur (activation des notifications) ne sont plus affichés. Vérifié sur un build de production : page en erreur → statut 500, rien de technique dans le HTML, code visible, journal complet sous ce code. 166 tests dont 8 de journalisation. **Option non faite** : un écran « Journal des erreurs » dans l'administration (stockage en base, filtre par code) ; aujourd'hui l'administrateur consulte les Runtime Logs de Coolify. |

### Écarts volontaires au PRD-V2 (tickets)

- Statut de paiement validé : le code garde `PAID` (le PRD-V2 écrit `VALIDATED`), pour ne pas toucher l'historique ni l'interface.
- Les tours sont **réservés au fil de l'eau** (ordre proposé dès le brouillon, par ticket) puis **figés et rattachés au cycle au démarrage**.
- Les tours annulés (membre retiré) restent en historique ; la règle « un ticket une seule fois par cycle » vaut pour les tours non annulés.
- Les tickets d'un membre retiré passent `INACTIVE` (conservés) ; `deletedAt` ne sert qu'à la suppression par l'administrateur avant démarrage.

## 7. Prise en main

```bash
npm install
npm run dev     # http://localhost:3700 — comptes de démo sur la page de connexion (mot de passe Koti2026)
```

Pièges connus :
- Les données de démonstration sont dans `.data/koti-demo.json` ; changer `SCHEMA_VERSION` (store) les régénère automatiquement.
- Une régénération invalide les sessions : il faut se reconnecter.
- Passage v2 → v3 : au premier démarrage, `.data/koti-demo.json` est migré (copie de sécurité `koti-demo.json.v2.bak`). Si la migration détecte une ambiguïté, le serveur refuse de démarrer avec un message précis et le fichier reste intact.
- Le limiteur de connexion bloque un e-mail 15 min après 8 échecs ; un redémarrage du serveur le remet à zéro.
